## 背景与决策

当前2024 epoch442模型已在Lite上完成PS/NPU混合执行、跨帧状态修复、九组27样本数值核验及短期性能定位。用户已接受现有样本的部署数值阶段，并明确要求先用当前方案实现项目全流程，再考虑真实指针映射/零拷贝、计算图或自定义算子优化。

首版采用已验证lazy-r4运行核心：保留SDK显式复制、Host暂存和受限CPU算子适配；Matmul继续执行于NPU，Gather继续使用原SDK实现。SDK profiling关闭，保留单一steady_clock计量能力及原校验/同步协议。优先推进电脑原始CSI回放→板端接收/预处理→异构推理→骨架绘制→HDMI与H.264 RTSP的闭环。

不以深度优化作为接入前置条件，也不把本决策解释为整机已经通过。首版目标仍为有效骨架更新≥5Hz、板端完整窗口到达至画面完成P95≤500ms、双路输出及30分钟连续运行；10Hz保持后续优化目标。

## 困境、难点与现行处理

| 难点 | 已掌握的依据 | 首版处理及限制 |
| --- | --- | --- |
| ARM Host注册不完整 | TopK/GatherElements/ScatterND未注册，官方便携内核存在；全CPU参考另有Matmul缺口 | 应用侧显式注册三类缺失Host算子，SDK旧条目检查后保持；不转全CPU，不把Matmul迁至PS |
| 内核不接受merged分布声明 | 当前图相关声明为完整有效范围，便携内核直接拒绝这些声明 | 校验轴/掩码/全有效范围/布局/字节数；仅临时内核描述去冗余分布信息，图和输出声明保持；非全有效或新规格直接拒绝 |
| PS/NPU内存跨域 | ADDR/BOTH不是已证实可直接解引用的CPU指针；SDK内存往返及实际Host暂存已验证 | 输入waitForReady后分配Host CPTR并SDK copyFrom，再执行CPU；提供输出时按SDK写回；当前真实模型未触发提供输出writeback，不扩大该路径验收 |
| Session部署改变节点身份 | 自动融合使原节点不再逐项出现在实际绑定中 | 按七实际ZG组及固定merge_from追溯1173原节点，保持唯一覆盖/同步基线；不降低检查数量或把原layer_count=0当缺绑定 |
| 连续帧读取首帧结果 | r5记录显示计数累积使本帧绝对阈值提前满足；r6修复已实测 | 沿用状态清理及最终完成协议，不做reset(0)、猜测cache/ready修改或并发forward；745仅对应当前固定图 |
| 验证核心尚非生产应用 | process_window目前要求冻结Tokens参考；输出接口含验证用字符串/证据管理 | 新生产接口与验证包装器分离，保留结构/有限性/身份/完成检查；固定参考逐位比较仍留在测试层，不把未知窗口强行匹配旧参考 |
| 核心性能余量有限 | 平均190.60ms，200ms周期平均余量约9.40ms | 先测网络/绘图/转换/编码及资源争用；平均余量不是每帧保证，也不是所有异步阶段之和必须小于9.4ms；整机关键路径、各工作者吞吐及队列须分别验收 |
| 候选排序与显示语义 | 离群帧交叉候选姿态更接近，14关节连接表来源存在冲突 | 最高分选择、不用GT或最近姿态重新匹配；保留原始坐标，确认展示连线/轴向再投影，不宣称人物身份稳定或物理单位 |
| HDMI/VPU配套不明 | 参考默认1080p/RGB565、VPU默认NV21/HEVC，与目标720p/H.264有差异；参考时钟不能证明当前位流配置 | 先核对现有BOOT/位流时序、buffer格式/stride/对齐/所有权；独立测试图后再接真实推理；不直接启动改变MMU状态的相机示例 |

## 单时钟测量揭示的性能约束

lazy-r4平均forward约183.26ms。下列跨度有嵌套关系，不能重复累加：

| 区间 | 平均/ms | 可作出的结论 |
| --- | ---: | --- |
| CPU桥输入就绪等待 | 164.4569 | 当前主要时间来源；含SDK等待/轮询及生产者就绪过程，不能直接当纯NPU计算或DMA时间 |
| CPU桥计算 | 13.6379 | 包含输入描述/有限性检查、内存管理及便携内核，尚不是纯算术指令时间 |
| CPU桥显式复制 | 0.4705 | 当前八份输入Host暂存的可见复制，不涵盖全部后端内部搬运 |
| CPU桥Host分配 | 0.1583 | 当前可见分配较小 |
| ZG后端调用合计 | 0.8453 | SDK提交/调用跨度；异步返回使它不能代表完整硬件计算耗时 |
| PS预处理 | 5.6103 | 输入到Tokens的本机板端处理 |

此前通过新增两个const char*错误消息重载，避免成功校验也构造临时std::string，处理均值减少22.33ms；所有检查及数学保持。该小修正已包含在首版基线，不需要重新优化或重跑已通过阶段。

即使完全消除当前可见0.47ms复制，也只对应约0.25%的处理耗时；这不是通用零拷贝收益上界，因为还未测全部内部搬运。但现有证据不支持靠指针映射直接消除164ms等待。

## 闭环完成后的可能解决方案

以下是候选研究方向，不代表SDK已提供可用映射、更优图已经生成或实施已获批准。按整机测量选择，先验证正确性再量收益。

| 方向 | 可能解决的部分 | 实施前证明与验证 |
| --- | --- | --- |
| SDK支持的真实指针映射/零拷贝 | Host暂存及部分复制/分配 | 明确物理/虚拟地址、region归属、cache属性、映射API、访问权限/对齐/stride、生命周期和生产者完成；BOTH也不能仅凭枚举转裸指针；校验正负零/边界、重复异帧及双路竞争，SDK不支持则保留复制 |
| 缓冲区复用 | 每帧分配及管理 | 证明张量布局和容量稳定、前帧消费者完成、无别名覆盖/悬挂句柄；不跨帧复用ready/计数，收益须超过引入复杂度 |
| CPU便携内核或自定义实现优化 | 约13.64ms CPU桥计算中的可优化部分 | 进一步分出检查/内核；保持TopK同值顺序、FP32索引、边界、ScatterND NONE语义及错误路径，固定/合成/异常和真实内容逐位回归；SIMD、专用内核或插件须单独证明ARM注册与生命周期 |
| 计算图优化、减少异构切换 | 排序/索引/Scatter与ZG的交接次数、内部搬运 | 找到受支持的图变换/融合和NPU算子约束；重编图可能改变布局/量化/绑定/计数，必须新包记录来源、重验数值和帧协议，不把静态算子支持等同当前图可直接NPU执行 |
| ZG编译与内存规划调优 | 真正硬件计算或内部访存瓶颈 | 先识别等待的来源，再基于官方工具研究OCM/ETM/内存复用等；保留旧模型和SDK，计数/融合基线随新图重建，不凭短调用跨度选参数 |
| 调度/队列与绘图编码优化 | 系统延迟、PS争用、积压 | 首版先单Engine串行、有界完整窗口和不可变结果帧；闭环测量后调整网络/输出工作者，不并发调用Session；重复编码旧画面不计有效骨架更新 |

不把Linux cache helper当作设备同步证明，不删除输入/输出有限性与布局检查，不改变模型精度、同步或BOOT来换取不可追溯的速度数字。

## 实施顺序与后果

当前决策降低首版集成风险，接受显式复制和受限算子适配的维护成本。继续追求10Hz和通用布局支持会增加模型、SDK/缓存与跨帧一致性的验证工作，故后置到首版闭环验收之后。

下一阶段按[首版全流程接入计划](../tools/pose-v1/FULL-FLOW-PLAN-20261007.md)推进：生产接口→网络回放→骨架画面→独立HDMI/编码RTSP→双路合并与长期验收。
视频配套核对可在软件接入准备期间进行；替换BOOT/位流、新依赖与设备初始化应在具体方案和已授权范围内逐项落实。

若闭环因吞吐/争用不能达到首版门槛，先记录失败与各阶段耗时；不降低≥5Hz/P95≤500ms目标或把旧帧重复当新帧。必要时提出最小集成瓶颈修正，不自行转全CPU或提前启动深度图/零拷贝优化。
