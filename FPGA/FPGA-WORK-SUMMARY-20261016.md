## 2. 已完成的工程内容

### 2.1 原厂资料、问题及引脚核对

- 按本地原理图、开发板手册、参考工程和实际BOOT逐项核对。独立参考时钟为AC14／100MHz，原MIG差分时钟输入保持；TMDS引脚沿用板卡原连接，详见[引脚契约](hdmi_candidate/PIN-CONTRACT.md)。
- 参考RTL仿真暴露原扫描时钟对应约80.81Hz、AXI在RREADY为0时提前计为完成，以及停止消费后读帧可能卡住等问题。参考源码仿真结果与当前原厂BOOT的实际内部行为分别记录，没有仅凭源码就宣称原BOOT所有故障均已实证。
- 核实`uihdmitx.v`两处字符串`"1111100000"`不等于10位二进制常量，改为`10'b1111100000`；目标7FAMILY模型验证时钟占空比由原20%变为50%。
- 原理图明确IO直驱HDMI对1080p60不作保证；本次稳定色条是所用板卡与显示器组合的实际结果，不能推广为所有线缆、显示器、温度或长期电气裕量保证。

### 2.2 模块实现与现行接口

| 功能 | 实现与状态 |
|---|---|
| 时钟与物理发送 | 独立100MHz输入，MMCM同一742.5MHz输出经BUFIO提供串行时钟，经BUFR／5提供148.5MHz像素时钟；保留7FAMILY TMDS编码／差分输出，规范序列器复位释放 |
| AXI读主机 | 只在RVALID且RREADY时消费数据；最多16拍、一次在途；按4KiB边界拆分；检查响应错误和RLAST，停止后排空已接受的读事务 |
| FIFO及RGB565 | 512×64位存储、低16位像素先出；完成同步RAM综合适配、指针回绕和部分字刷新验证。FIFO状态复位改为各时钟域三级同步释放，保留功能状态的恢复／移除检查 |
| 像素扫描 | 1920×1080活动区、2200×1125总时序，自由运行同步信号；STOP保持有效黑色扫描，START在帧边界采用，欠载上报并进入停止处理 |
| 命令／帧管理 | 单在途命令邮箱、多位保持总线、请求／响应同步、帧地址和ID采用、翻帧、停止标签与原子快照；这些逻辑已仿真，板端动态链路未验收 |
| 总线适配 | 新扫描器独占HP2的AR／R；原相机AW／W／B写路径保留。完整地址片选先于旧桥低位截断，CSR固定为`0x400b0000–0x400b00ff` |
| 静态诊断 | 内置八色条、PLL／空闲／错误状态、像素Gray计数、CSR计数和双ABI；静态探针使用原公开SDK，不申请显示帧或创建推理Session |

核心源码位于[rtl目录](hdmi_candidate/rtl)。九个逻辑模块为`hdmi_axi_read.v`、`hdmi_stream_fifo.v`、`hdmi_scan_control.v`、`hdmi_command_mailbox.v`、`hdmi_register_bank.v`、`hdmi_candidate_core.v`、`hdmi_candidate_register_core.v`、`hdmi_pixel_scan.v`和`hdmi_scanout.v`。最后一轮复位修正只修改其中FIFO，另外八份在该轮保持。

整机适配源码为[hdmi_board.sv](hdmi_candidate/rtl/integration/hdmi_board.sv)、[hdmi_cam_router.sv](hdmi_candidate/rtl/integration/hdmi_cam_router.sv)和[hdmi_clock_jfm.v](hdmi_candidate/rtl/integration/hdmi_clock_jfm.v)。隔离原厂工程中还修改了顶层、PS外围连接、旧显示分支选择、TMDS常量及序列器复位五份参考RTL；原参考目录未回写。

core ABI为`0x48444d01`，板级适配ABI为`0x48445301`。`0x30`中的同步idle仅用于诊断；后续释放实际帧块必须依据原子快照、响应代数和stopped ID。候选允许地址范围`0x30100000–0x38100000`不代表软件拥有整段内存，后续仍须核实公开SDK实际分配的块和写入完成契约。

详细连接、寄存器、参数和资源所有权见[整机集成说明](hdmi_candidate/SYSTEM-INTEGRATION-PLAN.md)。这些是当前已经实现的结构，不替代下一阶段PS／NPU／PL分工讨论。

## 3. 对原厂工程、位流与BOOT实际做了什么

### 3.1 基线身份及原厂链路复现

所选原BOOT来自用户指定的本地目录：

```text
D:\Dowload from Chrome\嵌赛资料\Icraft\参考实现\位流\悟净LITE版_BOOT_25122301_单路PLIN+pHDMI(外置detpost)\悟净LITE版_BOOT_25122301_单路PLIN+pHDMI(外置detpost)\BOOT.bin
```

我读取并解析其PL分区，将32位字节交换后的配置载荷与原厂回退bit核对，保留原BOOT和回退bit。随后在隔离工程复现原厂构建链，生成参考bit并执行原厂Procise后处理；比较证明该参考输出的**完整配置载荷**与所选BOOT的PL载荷相同。文件头、日期和文件SHA不同不代表配置功能不同，因此没有把参考重建作为HDMI修复或重复下载验收。

原BOOT离线重封装曾完整复现。另一次试制BOOT仅有9个映像名称字节改变、PL不变，严格后检失败并停止；原文件和失败记录保留。见[参考载荷比较](../tools/pose-v1/evidence/hdmi-board-reference-20261016-r1/reference-payload-review.json)。

### 3.3 BOOT封装与板端临时启动

1. 使用所选版本的原`FSBL251210_ddr400_demo.out`、`bl31.elf`、`u-boot`和原厂BIF参数，仅换入新PL bit。保持原bit映像文件名，避免无关名称字段改变。
2. 离线核对BOOT：PL分区起点186,816字节、分区长度5,980,464字节；新旧BOOT仅该分区中2,007,499字节不同，全部非PL字节及填充相同。三份PS启动输入身份保持。[离线封装核验](../tools/pose-v1/evidence/hdmi-integration-20261016-r1/boot-offline-r5/review.json)。
3. 重新核验JTAG-HS1及实际器件链，建立回退资料；**JTAG只执行枚举和扫链，没有调用`program_bit`加载本候选。** 实际候选通过临时BOOT和FSBL加载。
4. 用户另行明确批准临时启动区替换与一次候选重启。实际备份并回传板端原BOOT，核对候选，临时替换启动分区BOOT、同步卸载；打开UART记录后执行一次受控重启。
5. 新Linux／SSH恢复后，先还原原BOOT文件，完整读回原SHA，并核对其余启动文件与六份SDK不变，再运行静态探针。未修改uEnv、DTB、内核或模型，没有永久安装候选BOOT。

**最后已验证状态：板端启动文件为原BOOT，运行中PL保留新HDMI候选；下次正常启动会选原配置。** 文件恢复不等于运行中PL已回退。一次候选重启已使用，必要时的一次回退重启未使用；当前暂停期间不会自行调用历史许可。

## 6. 暂停状态与后续架构讨论所需信息

本次只整理记录，没有启动新的综合、仿真、下载、板端命令、文件系统修复、DMA或后台监测，也没有为了暂停改变板端输出或再重启。关于运行中候选／原启动文件的描述来自上次封存验证，本轮未重新读取实板状态。

后续讨论可依据以下既有边界，不预先指定新的任务分工：

- 当前PL已经承接HDMI扫描时序、序列化和候选读帧／停止控制逻辑；真实DDR读帧仍待硬件验证。
- PS仍负责公开SDK资源拥有、命令提交与错误处理，实际帧块必须有可核验的所有权、写入完成和释放顺序。
- 共享模型和NPU分配保持既有状态；CSI预处理或心率检测尚未被本阶段迁入PL。
- 未来若采用本候选，需分别讨论正式显示接口、帧资源生命周期、与推理／RTSP并发的实时目标，以及启动分区FAT问题与长期部署方式。

这些是待讨论项，不是新的实施计划。恢复须先取得用户确定架构后的明确执行指令，再核验当前板端运行身份、BOOT和资源，不能永久假设上次运行状态仍在。
