# TopK=1、无置信度阈值启动包

2026-10-28 当前交付仍为 r4 生命周期加固版本，保留 r3 父死亡清理、r2 单人滤波和原迁移训练 epoch99 的 180-query 计算图。包内包含 ARM64 程序、原 JSON／RAW、合格 BOOT 备份、独立 PC 页面和对应核心源码。依赖开发板已经安装且身份一致的 Icraft／customop 3.39.0；PC 使用 Node.js 20 或以上。

**用户要求暂不更新启动包。** 下方板端异常资源保护已修改工作区源码并完成本地验证，尚未打包或部署；现有 r4 归档不包含这些修订，启动包选择保持 r4。

每个有效输出从 180 个候选中取最高分 1 个，同分按候选索引；**没有置信度下限**，零分也不会因分数被丢弃。r2 显式开启 `--single-person-stability 1`，保留有限值检查、初次三次确认和 250 ms 可见保持，因此不能理解为任何输入下都强行画出一个人。无人时模型仍可能给出单人候选。

单人模式在滤波更新前隔离位置／形状突变；新位置至少连续 4 次、跨越 180 ms 相容观测后才接纳，初次确认至少跨越 90 ms。它保留原始 Top1 和原始坐标，不以次高分候选替代。确认后的切换保留滤波状态，分别平滑中心与相对姿态，并按先前身体尺度限制单次显示变化，将限幅反馈至滤波状态。基础参数仍为 `0.5／0.3／1`，中心使用 `0.35／0.15／1`，相对姿态使用 `0.5／0.2／1`。

旧观测最多显示 250 ms，隐藏锚点最多保留 1 s；恢复代次切换或长时间缺失后重新确认。拒绝期间不会续写有效观测时间，也不会在缺少新数据时外推。原 v5 模式可用 `--single-person-stability 0` 离线对照；单人增强模式只支持 CPU Top1。更强抑制会增加动作延迟、短暂保持或空显示，不能保证没有模型误判。

输入为三 RX 实时 CSI，使用现有自适应容限、后台重匹配及完整窗口边界切换，保留原预处理。HDMI 和 PC 使用同一份已跟踪结果；PC 更新为识别 `score_threshold: null`，不会再次套用旧的 0.2 限制。原始 180 路输出和帧协议保持。

## 开发板手动启停

将整个包解压到开发板可写目录，进入包根目录，以 root 执行：

```sh
sh check.sh
sh start.sh
sh status.sh
sh stop.sh
```

默认持续运行至手动停止；也可 `sh start.sh --seconds 600` 指定有限处理期。程序正常释放 SDK／HDMI 后才记录完成，停止请求不强杀在途 SDK。每次手动启动创建独立 `board/runs/` 记录；缺少上次安全关闭证明时拒绝同一次 Linux 启动内重试。没有自动重启或 SDK 开机自启动钩子。

启动时只按需增加本轮临时 `eth0` 地址 `192.168.50.49/24`，正常关闭后移除本轮增加的地址；预先存在的地址和其它网络设置保留。复用四台路由器已经安装的 CSI 服务，包本身不登录路由器、不恢复先前测试、不重装驱动。PC 不参与板端采集和推理调度。

当前已核对的 Linux boot_id 可直接准入。若设备已经重启而启动器报未知 BOOT，先在所有设备占用释放、启动文件与已发布 BOOT 一致时运行：

```sh
python3 board/startup.py prepare-boot
# 随后由操作人员明确安排一次正常重启，再执行 start.sh。
```

准备操作只读核对启动分区并记录身份，不执行 BOOT 写入或重启。包内 `boot/BOOT.BIN` 为已发布合格版本的备份，启动器不会自动安装它；若核对发现启动文件不同，应先查明当前设备状态。原生 HDMI 功能 ABI、独占、idle／STOP／drain 检查继续生效。

## 可选 PC 输出

在 Windows PC 包根目录运行 `start-pc.ps1`，随后打开 `http://127.0.0.1:39380/`。默认连接 `192.168.50.49:39385`；`-Board` 可指定开发板诊断地址。按 Ctrl+C 关闭 PC 页面服务，板端仍独立运行。

两路布局及七色条待机沿用已发布系统。PC 必须使用本包观察端，旧观察端会拒收低分结果。`core-sources.tar.gz` 保存本次直接使用的核心源码及构建入口；构建 `pose180_demo` 时设置 `POSE180_BUILD_SDK=ON`、`POSE180_DEMO_PROBE_FREE_DRAIN=ON`、`POSE180_DEMO_PL_FILTER=ON`，使用已有 ARM64 SDK 工具链。

## 验证与当前状态

### 板端异常资源保护源码修订（未打包）

对下节复核确认的三个缺口完成应用层修订。HDMI 在构造中途失败、且本轮尚未提交 START／FLIP 时，显式回收已经分配的帧块；逐块记录释放尝试和完成状态，避免某次 `free()` 抛出异常后再次释放同一块。STOP 只提交一次，成功证明保留供后续清理使用；释放结果未知时仍采用既有退出码 70 的保护，不自动重试 STOP、free 或负载。非标准异常也进入该保护。

Runtime 在设备初始化、设备就绪回调、输入写入、状态清零、forward／最终等待及首次输出读取期间记录未完成操作。两份输出句柄改由 Runtime 持有，等待失败时不随局部变量提前析构。正常同步调用返回或原有的两输出就绪／实际图完成计数检查通过后，才允许对应资源释放；不新增完成语义或用超时当作完成。Runtime 初始化分成对象构造和初始化步骤，使构造期间的硬件异常也经过释放保护。

若无法证明安全，状态为 **`release_blocked`**：停止新推理，不释放已持有的 SDK 句柄、输出缓冲和全局独占锁，控制接口继续可读；不写 `native_shutdown_complete=true`。初始化前的功能启动控制也采用此保护，避免没有 Runtime 对象时错误地宣称已关闭。TERM／INT／HUP、时限到达或守护进程消失都不会解除保护；`recover.sh` 拒绝该状态。此时 `stop.sh` 仅表示请求已发出，**不能理解为资源已释放**，需要另行核验和受控硬件恢复。没有新增自动复位、BOOT 操作或 SDK 重试；SDK 内部抛出异常时自行销毁的私有对象仍不受应用层控制。

原生初始化、推理、等待画面和最外层补齐非标准异常接收；诊断写入失败不掩盖原错。数据集线程及保留的严格入口也补齐相关收尾。正常有完成证明的故障继续走关闭／释放路径；真实 SIGKILL、SIGSEGV、断电仍不能保证物理资源安全回收。

本地验证通过：实际 HDMI 实现配合公开接口替身完成 9 类分配／校验／重复关闭／未知释放场景，部分构造失败时原先 4,147,200／8,294,400 字节未释放计数均归零；未知 free 不重复调用。释放守卫测试证明正常完成会释放、未完成的初始化／等待异常不会析构所持有的资源或丢失独占。原生 mock 验证非标准异常可隔离后正常退出；未证明场景在 TERM 及守护死亡后保持句柄边界和独占、状态可读、没有成功完成回执、拒绝恢复。另通过 r4 生命周期、退出、无阈值及常驻故障回归，以及常驻／严格两个 ARM64 目标构建。验证记录保存在历史命名的 `.local/pose180-top1-no-threshold-20261028-r5`：[构建记录](../../../.local/pose180-top1-no-threshold-20261028-r5/build.json)、[回归记录](../../../.local/pose180-top1-no-threshold-20261028-r5/verification.json)、[最终原生故障注入](../../../.local/pose180-top1-no-threshold-20261028-r5/native-safety-final/result.json)。该目录仅为源码验证工作区，没有生成 r5 启动包；以上均未执行真实 SDK 或修改设备网络，不代替板端故障恢复验收。

### 板端 C++ 专项复核：r4 仍有的缺口

以下保留 r4 复核时的发现，后续源码修订见上节。2026-10-28 检查实际 `pose180_demo` 链接的 `board/runtime.cpp`、resident C++ 和 `native_rgb565_r53/display/hdmi_output.cpp`，并对照本机 ARM64 Icraft 3.39.0 头文件，确认 r4 的上层生命周期验证不能覆盖以下底层异常；原复核仅做本地复现，没有连接设备。

- **HDMI 部分构造缺少回滚。** 帧分配使用 `malloc(frameBytes, false, 64)`，但构造中途抛出异常不会执行 `Output::~Output()`，已有帧也没有显式释放。直接编译现行 `hdmi_output.cpp`，用按公开接口实现的替身注入第二次分配失败／第二块地址越界：释放调用均为 0，应用层未释放字节分别为 4,147,200／8,294,400；正常关闭对照为两次释放、残留 0。板端驱动是否会在进程消失后回收这些物理块仍未知，不能把替身计数写成实板 CMA 泄漏实测。修正应限于尚未 START 的本轮已分配块，并记录部分释放进度。
- **NPU 在途异常缺少独立释放门。** `Runtime::infer()` 在 forward／最终等待异常时重抛；本机 SDK 的 `waitForReady()` 超时仅返回 false，没有取消硬件工作。局部输出句柄会退出作用域，随后停止流程仍销毁 Runtime／Session／Device，并写 `native_shutdown_complete=true`，没有显式的 NPU 停止／排空证明。HDMI 的 STOP 证明不涵盖 NPU。SDK 二进制析构内部是否等待尚未得到保证；应在核实其停止契约前保留未完成句柄，区分停止未证明与安全完成，不能靠普通析构或上层禁止重试替代。
- **非标准异常可能越过正常收尾。** Runtime 会捕获并重抛 `catch (...)`，而原生初始化、处理循环和最外层只接 `std::exception`；此类异常可能进入 `std::terminate`，不能保证完成 HDMI STOP 或 SDK 清理。此项为源码路径判断，尚无实板发生证据。

原检查证据见[本地结果](../../../.local/board-core-lifecycle-audit-20261028/result.json)。r4 归档保持不变，工作区源码已完成上述应用层修订；“构建／mock 通过”仍只适用于列出的已测范围，不代表所有底层异常均能安全释放。

### 启动、停止与清理衔接（r4）

启动器在初始化、运行和清理全程接管 TERM／INT／HUP，记录停止请求并在进入下一阶段前检查；重复信号不会打断已开始的收尾。原生程序也把 HUP 作为正常停止请求。已有停止请求时不启动原生进程；`stop.sh` 即使无法写入停止文件，也会核验 PID／启动时刻／boot_id 后发送正常停止信号，支持时使用 pidfd 固定进程身份。

启动、原生退出和临时地址清理处于同一段全局独占期。新增 `/run/pose180-resident.active.json` 保存本次 Linux 启动内的最近运行目录，使采用 r4 启动器的不同包目录也检查同一个未完成负载；旧包目录不能移走或删除后绕过未证明的释放。过期的启动请求无法在新预约之后启动 SDK。只有本版入口遵守这条记录，不能据此宣称任意旧脚本或直接执行程序都受到同样保护。

临时地址在修改前记录独有的接口 label，新增操作后即使抛出异常，清理仍可读取原记录。撤销时核对地址、前缀和 label；已有地址保留，若同地址已经被其它操作接管则停止撤销并记录待处理。记录写不成功时不会修改网络；待清理事项解决前不覆盖旧运行入口。`recover.sh` 仍只在核验安全关闭后手动收尾，不启动 SDK。

监控异常请求原生正常停止，等待其真正退出后保存实际完成证据；日志关闭报错不再中断其余清理。内存采样不可用记为未知，不当成零可用内存；状态读取采用 200 ms 总预算，逐字节慢返回不会无限拖住停止检查。资源证明损坏或缺失仍采取阻断处理。

本地新增故障测试通过：初始化和重复清理信号各 3 类、两处启动前停止、临时地址写前记录／写入失败不修改网络／外部接管地址保护、清理持锁、跨目录启动保护、过期请求拒绝、监控异常和慢状态连接。完整 CLI 连续启停 3 轮，3 次并行包启动均被拒绝，3 次停止标记模拟写满仍正常退出；mock 原生关闭证明均为 true。FD 数恢复 4→4，已有 r3 退出及常驻故障回归通过。地址命令均用替身验证，没有实际修改 PC 或开发板网络。本轮只增加 HUP 正常停止处理，未改变 SDK、HDMI STOP／drain、模型或滤波数学。

### 异常退出与资源释放检查（r3）

检查并在本地 mock 中复现：旧 r2 守护进程被 SIGKILL 后，原生进程仍继续运行。r3 通过 Linux 父进程死亡通知向原生进程发送正常 SIGTERM，在途调用返回后按原顺序关闭；独占锁描述符同时由原生进程持有，避免守护进程先退出就允许第二个负载进入。忽略日志管道断开产生的 SIGPIPE，避免日志进程死亡间接终止在途 SDK。

Python 日志泵和原生归档子进程均绑定父进程生命周期，归档子进程关闭继承的独占锁等额外描述符，并恢复可终止的日志信号处理。磁盘写满不再让关键监控写入跳过清理；日志创建／程序 exec 失败会关闭已有管道和回收日志进程。日志等待有界，内核不可中断文件 IO 仍可能留下待回收的非 SDK 日志进程，不能因此宣称所有 Linux 资源必定立即消失。

启动器增加孤立原生进程识别，`stop.sh` 可向仍可核验身份的本包孤立进程请求正常停止。临时地址仅在本轮未启动 SDK，或实际关闭已证明且无进程／设备占用时撤销；原有地址保留、重复清理可重入。守护进程异常退出后若原生已安全结束但监控回执／地址清理未完成，可手动运行：

```sh
sh status.sh
sh recover.sh
```

`recover` 只检查现有关闭证明、占用和同一次启动身份，处理本包临时网络及恢复回执；不启动 SDK、不重试推理、不回写原失败记录。已知失败 SDK、缺少真实关闭证明或仍有占用时拒绝恢复。若 SDK 调用一直不返回，继续等待并保留独占，不能以超时为由强杀和释放。

**真实原生进程遭 SIGKILL／SIGSEGV、断电，或 HDMI STOP／drain 无法证明时，仍无法保证硬件资源已经安全释放。** Linux 回收文件描述符不等于 PL 停止或 SDK 物理块回收；HDMI 现有 `_Exit(70)` 保留资源的保护继续有效。此时标记释放未证明并禁止同次启动内盲目重试，需另行核验硬件及受控恢复；本轮未上板执行这些故障。

本地检查通过：旧版孤立进程复现及新版父死亡正常退出；慢调用期间独占仍有效、退出后释放；四轮监控写满后 FD 数 4→4；exec 失败、端口被占导致部分初始化失败时的清理；暂停归档进程后强杀 mock 原生，归档被回收、端口释放且释放证明为 false；三种网络清理分支、手动恢复证明／拒绝、重复清理。仅在进入任何 SDK／功能 MMIO 之前失败时，原生程序才补写“硬件未开始”的关闭回执，用于撤销本包地址；进入硬件阶段后失败仍保留隔离与重试保护。另通过原有慢调用、记录暂停、慢／断开的 PC、磁盘故障恢复、部分输入断开和异常隔离检查。强杀只施加于本地 mock，未接触板端 SDK。
