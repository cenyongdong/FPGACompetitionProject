## FD 计数失败原因与异常退出复验

2026-10-29 后续专项已确认：失败来自测试线程退出与句柄采样之间的竞态。慢状态连接测试的 `worker.join()` 返回时，Python 线程结束标记已释放，底层 pthread 仍可能在退出过程中首次加载 `libgcc_s.so.1`；抓到了该库及 `/etc/ld.so.cache` 的临时文件句柄。旧 `len(list(/proc/self/fd))` 又包含枚举目录自身的短暂句柄，正常基线因此为 4。临时加载期间会读到 5，随后的实际打开句柄只剩标准输入输出。

独立最小复现不运行推理、SDK 或监督器：16 个新 Python 进程中，15 次在 `join()` 后仍能看到对应内核线程，7 次旧计数得到 5；16 次均在内核线程退出后恢复原句柄集合。实际测试本身也在新进程中重新复现 4→5。逐行跟踪带来的额外耗时会掩盖该短暂窗口，解释了此前跟踪复验通过。

修正位于 [test_startup_robustness.py](../control/test_startup_robustness.py) 和 [test_exit_cleanup.py](../control/test_exit_cleanup.py)：等待该测试线程的 `/proc/self/task/<native_id>` 消失后再核对资源；采样目录枚举结束后仍存在的 FD→目标映射，比较完整集合，失败时直接报告多出的句柄。保留 2 秒有界等待；没有改变生产程序、SDK 释放规则或硬件配置。负向检查主动保持库文件、管道和 socket 打开，三类额外资源均被识别。

| 本轮实际检查 | 结果 |
|---|---|
| 8 个新进程的完整生命周期检查 | 全部通过，共 24 次 CLI 启停；监控前后真实 FD 均为 3→3，进程／端口／独占按用例回收 |
| 启动前管道设置、日志进程启动失败 | 新增 2 项故障注入；两端管道均回收，原生程序未启动 |
| 监控异常、磁盘写满、exec 失败、端口冲突 | 正常退出与部分初始化清理通过；4 轮写满后 FD 为 3→3 |
| 监督进程被终止、原生异常 | 在途 mock 保持独占至正常完成，随后回收子进程与锁；非标准异常隔离后正常释放 |
| 原生 mock 被强杀 | 日志子进程和端口回收；关闭证明保持 false，不把进程消失当作硬件安全释放 |
| 完成未证明与 HDMI 接口替身 | NPU 守卫保留资源／独占并拒绝恢复；HDMI 9 类分配、STOP 与释放用例通过，已完成路径回收，无重复 free |
