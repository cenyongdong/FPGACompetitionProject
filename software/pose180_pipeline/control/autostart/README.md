# 四路 CSI 路由器开机服务

2026-10-25，用户授权将自有 TX／RX 固定为开机自启动。本功能只控制四台路由器；板端 BOOT、SDK、接收程序与 HDMI 启动仍独立管理。它不恢复任何旧板测包的次数。

## 设计与启动顺序

- 固定角色：RX1 `.50.1`、TX `.50.2`、RX2 `.50.3`、RX3 `.50.4`。LAN、DHCP、认证及接线保持，管理链路不依赖被替换的 WLAN 模块。
- `/jffs/scripts/services-start` 保留原 KoolShare 调用，追加独立启动入口。每次开机只自动尝试一次；等待系统启动至少60秒、`eth6`和本机 IP／MAC 就绪，再装入已验证的 Nexmon 模块。重复钩子不会创建第二个发送任务。
- 持久资产在 `/jffs/pose180-csi`，运行时拷贝到 `/tmp/pose180-csi`。常规状态与日志只写 RAM；守护事件两段各约64KiB，捕获末次回执最多4份，保留至多一个上次手动运行目录，无逐包闪存归档。
- TX沿用r6的mode3／300Hz／信道161/20，单任务每10秒续期，固件60秒租约保护保持。不按60秒结束或重配；不依赖PC或开发板心跳。
- RX开启三天线CSI，来源过滤为TX无线MAC `f0:2f:74:39:45:6c`，直接连接开发板 `192.168.50.49:39033`。板端未启动时按2／4／8／16／30秒退避；服务恢复后自动接入。单路仅有64KiB用户态转发缓冲，积压超过500ms即丢弃连接并重新采集。
- 持久服务显式使用 `continuous` 标记及时长0；TX还必须有 `tx.lease`。持续捕获仅允许输出到管道且时长／包数同时为0，不再因原3600秒／400万包上限主动断流。有限板测模式和有限文件采集的原上限仍保留。
- 心跳超期先请求正常停止；未证明TX停止／释放，或拥有者仍在运行时，不强行卸载无线驱动，也不盲目重新启动任务。固件租约仍会在失去续期后到期；异常状态保留供检查，不做无限驱动重载或路由器自动重启。

因此路由器与开发板**没有严格上电先后依赖**。建议先给四台路由器供电，再启动板端服务，减少首次等待；晚启动、拔插或重启板端时，RX会自行重连。TX可在板端关闭时持续发射，此时RX不积攒离线数据。PC完全可选。重新应用路由器无线设置可能覆盖临时无线状态，应先停止此服务，操作后再启动。

## 查看、启停与禁用

SSH登录所需路由器后执行；四台命令相同。运行态和自启动开关分别控制：

```sh
# 查看角色运行状态、TX续期数／RX字节计数及错误
sh /jffs/pose180-csi/service.sh status

# 本次停止，恢复原厂无线运行时；下次开机仍自动启动
sh /jffs/pose180-csi/service.sh stop

# 手动再次启动已启用的服务
sh /jffs/pose180-csi/service.sh start

# 关闭开机自启动，并正常停止当前服务
sh /jffs/pose180-csi/service.sh disable

# 恢复开机自启动，并启动当前服务
sh /jffs/pose180-csi/service.sh enable
```

`backoff`且`fault=0`表示等待板端接收服务；`transmitting`且`TX_renewals`增长表示TX单任务正常续期。不能以这两个状态单独声称NPU／HDMI已经运行。

已有有限包的 `load.sh`／`router_ctl.sh start` **不能与本服务并行使用**。后续板测应复用本服务，仅开启板端`.50.49`和TCP39033；确需替换路由器模块时，先停止四台自启动服务并确认恢复。板测结束只关闭板端负载时，RX回到等待状态，TX继续运行。

## 部署与验证记录

打包入口为[prepare.py](prepare.py)，安装入口为[install.sh](install.sh)，服务为[service.sh](service.sh)。所有四机固件原件及既有开机脚本保留；未改 `/jffs/dhd.ko` 或原厂驱动。实际包、SSH原始回执和测试结果集中于 `.local/router-autostart-20261025-r1/`，最终修订包身份见 `package-final.json`。

离线通过：ARM64静态编译；19个TX租约场景（含常驻68秒跨租约、有限模式、超时、身份错误及停止证明）；RX晚接入／断开重连；持续管道捕获及正常停止；重复开机钩子、独立停止／再次启动／禁用。首次实机发现固件不提供`seq`，已改为POSIX计数循环并复测，未影响无线驱动或硬件。

四台已安装、正常停止并各实际重启一次，启动身份均改变；均自动恢复到161/20，三RX为monitor1、TX为monitor0，每台只有一个守护进程。再次调用boot／start，PID保持不变。最后采样TX同一任务运行约214秒，续期21次、续期失败0。

板端仅运行有限CPU接收检查，两段各45秒、中间关闭监听5秒。三RX均从原等待状态自行接入，并在监听恢复后重新连接；共收到180,989条CSI和同数NMD3记录，检查到的头部／TX来源／信道错误为0，六份捕获回执的kernel_drops均为0。RX1第二次主动关闭接收端时保留原生写管道错误回执，守护正常回到等待、fault=0；不将主动断流末尾未送达数据写成零丢包。

截至本轮结束，四台开机开关保持启用：TX持续发送，三RX等待板端服务。临时CPU接收程序已退出，板端临时`.50.49`已撤销，原BOOT身份不变，未运行SDK／推理／HDMI。具体原值、启动身份和运行状态见本地 `result.json`／`router-receipts`；后续联合板测接入说明见 `HANDOFF.md`。为已协调的下一轮板测保留PC临时`.50.102`和TX／RX3 LAN SSH，由接续验证任务收尾；这些诊断连接不是自启动依赖。此次短测不代表全天稳定性或模型／HDMI验收。

开机钩子机制参考[Asuswrt-Merlin User scripts](https://github.com/RMerl/asuswrt-merlin.ng/wiki/User-scripts)，并已核对四台实际固件、原有脚本和JFFS可用空间。
