# 异常数据块的下一有限取证

本轮纯计时分离及Host失败捕获已实现，Host107／真实Host192拒绝探针通过；原三窗首帧188出现NaN并保存输入，硬件阶段已停止。详见[结果](FORWARD-TRACE-R3-RESULTS-20261009.md)。不重跑r1/r2/r3、不放宽finite/索引门禁或推进103负载。

下一个隔离r4优先辨别数据异常位置，而非继续尖峰计量：

1. 保留正常路径；失败时先保存现有Host暂存720字节和错误，再记录对应SDK源Tensor的类型、区域、chunk身份、offset、容量、声明、可用的公共地址元数据。禁止直接解引用ADDR/BOTH。
2. 在异常后的同一有界上下文里，通过Tensor::read分别读取同一个源Tensor两次并独立拥有、保存；每次最多已验证声明字节数，单次合计不超过原失败输入范围，两次总量不超过其两倍，无新增模型forward、reset或原始寄存器读写。这是**新的设备源读取诊断，尚未实施/执行**，与本轮Host-only捕获分别记录。
3. 比较两份源读回、现有Host暂存及同CSI历史参考，按128/256字节偏移报告。源正确而暂存错误时调查copy/Host存储；源本身同样异常时调查NPU输出和潜在其他写入者；两份源变化时调查完成状态和数据生命周期。结果只缩小范围，不直接认定缓存、VPU或SDK根因。
4. 优先匹配实际ARM SDK二进制和MemChunk/区域read/copy路径；Linux cache helper是no-op不能作为同步证明，不添加手动cache/helper、sleep、复位、清缓存、修改BOOT/CMA或截断索引。
5. 新源码／身份／Host107与SDK-free捕获契约门检；只做一次最多180秒原三窗重复的有界诊断，异常完整回传并停止。无设备读回前不称搬运修复；成功也先与历史完整数值和真实视频来源核对。

当前720字节中[0,128)、[256,384)、[512,640)共96个FP32被95个零与一个0xffffffff替代，其余84个与旧308桥输入逐位一致。这是数据块异常证据，不是微小定点误差。来源机制和VPU关联未证；不将规整当作浮点数据修复。
