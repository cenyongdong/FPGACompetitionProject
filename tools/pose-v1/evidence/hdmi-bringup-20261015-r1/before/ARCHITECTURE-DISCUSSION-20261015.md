## 一、项目阶段与已确认方向

用户要求先理解已完成工作、模块结构和项目分工，再讨论后续架构；随后明确选择下一阶段使用共享细化模型。后续讨论沿用以下原则：保留现有模块和资源所有权结构，以共享模型完成正式链路接入，再根据实时性目标和比赛中 FPGA 的实际贡献确定 PL 职责。

最近实际进度以 [PROJECT-PROGRESS.md](PROJECT-PROGRESS.md) 和 [ADR_48](ADR/ADR_48.md) 为准。共享模型已完成三个固定输入窗口的基础验证、30 秒 1131 次和 30 分钟 62945 次连续串行推理验证。30 分钟实验的引擎均值约 23.27822 ms，P95 约 23.451264 ms，P99 约 24.494967 ms；存在 11 次超过 1 秒的异常长耗时，最大约 4.158 秒，发生于 forward 范围，D41 尚未闭环。这些结果不能证明新鲜连续 CSI、视频叠加或整机实时性能。

共享图由 1021 个 HardOp 合为 5 个 ZG 分组，最终 612 个操作；保持两级 TopK、100 个候选和 14 个关节，移除 ScatterND。现有正式 demo 仍使用旧图；共享模型的独立实验通过不等于正式链路已经接入。

现行数值比较契约为 ADR_48 v2：输入和全部分数逐位一致；以 FP32 参考 score>0.2 的候选为位置硬门检对象，最大关节三维欧氏偏差不超过 3 mm；低分候选保留诊断。所有候选的非有限值、非法索引、SDK 异常、身份变化仍停止。该例外不适用于旧 DATA 调查或其他固定基线。

## 二、模块、资源所有权与 PS／NPU／PL 分工讨论

软件核心保持 input、inference、diagnostics、display、video、stream 六个模块；software/demo 负责组合与生命周期管理，历史 pose_v1 和独立 engine_timing 实验不直接充当正式模块接口。各功能通过明确的最小接口协作，不通过包含其他模块的 .cpp、读取私有状态或复制算法接入。

讨论中的职责框架如下，具体 PL 功能尚未最终选定：

| 单元 | 讨论中的职责 | 边界与尚待确定事项 |
| --- | --- | --- |
| PS | 输入组织、预处理、调度、Host 算子、候选选择、绘制、网络与错误处理 | 保持线程和资源归属；共享模型先接入现有正式链路 |
| NPU | 已转换模型中实际分配给 ZG 的神经网络计算 | 不把 Host 回调耗时算作纯 NPU 时间；不擅自改变模型数学与分配 |
| VPU | 视频编码 | 与 HDMI 扫描输出是不同路径，分别验收 |
| PL | 候选为 RGB→NV12、CSI 预处理、特定 TopK／数据处理 | 需要先测瓶颈、明确接口与端到端收益，再决定实现范围 |

此前倾向优先评估 RGB→NV12 的确定性、独立性与比赛展示价值，但这只是候选建议，并未批准开始 RTL 开发，也未承诺吞吐提升。CSI 预处理和 TopK 同样需要测量与可实现性证据。现有约 23 ms 的引擎均值不能直接换算成整机稳定帧率；必须分别观察首次启动、常驻正确性、数值一致性、视频映射和吞吐。

## 三、CSI 心率功能讨论

用户提出增加通过 CSI 检测心率的健康功能，并要求先暂停此前任务划分讨论，分析 PL 实现可能性。参考项目为 [RuView](https://github.com/ruvnet/RuView)。用户随后明确：目前没有 CSI 采集设备，也没有心率数据。

心率估计确实通过数学和信号处理计算得到，但计算的输入必须包含真实心搏造成的无线信道细微变化。已有姿态输入、随机序列或重复播放的三个窗口不能自动变成可验证的心率数据。参考心率设备用于判断估计是否准确，并不是算法运行的必要输入；缺少真实 CSI 时，只能验证算法与硬件实现的一致性，不能验证真实心率检测能力。

已查看的 RuView 实现包括：

- [Rust heartrate.rs](https://github.com/ruvnet/RuView/blob/main/v2/crates/wifi-densepose-vitals/src/heartrate.rs)：利用幅度残差与相邻相位相干权重，经心率频段谐振／滤波、相关峰搜索与置信度计算。默认 56 个子载波、100 Hz、15 秒窗口，最少约 5 秒。0.8–2 Hz 处理频带约对应 48–120 bpm，不能将最终合理性范围当作实际全频段覆盖证明。
- [ESP32 edge_processing.c](https://github.com/ruvnet/RuView/blob/main/firmware/esp32-csi-node/main/edge_processing.c)：包含相位展开、统计与子载波选择、双二阶滤波、自相关以及呼吸谐波抑制，依赖时间戳与实际采样率。
- RuView 的合成回归样例证明软件行为，不能替代真实 CSI 的准确度或临床验证。
- [PhaseBeat 原始论文](https://www.eng.auburn.edu/~szm0001/papers/PhaseBeat_ACMHealth20.pdf)提供接收天线相位差等实验依据；其受试条件、天线与采集配置、静止要求及参考设备不能直接迁移为本项目的精度承诺。

PL 可实现有界缓存、去趋势、相位处理、滤波、统计、自相关或频谱等确定性计算。当前主要不确定性是采集设备、CSI 格式、天线关系、时间戳、丢包、采样率、运动干扰与可验证信号，而不是单纯缺少乘加能力。

候选架构是在原始连续 CSI 进入“仅保留最新姿态窗口”的覆盖槽之前分支，心率支路维护带时间戳的连续窗口；PL 做经过选择的信号处理，PS 做配置、质量判断、结果展示，NPU 继续姿态推理。现有 20 样本姿态窗口、2 Hz 回放节奏均不能直接当成心率支路的采样时钟。

当前仅完成可行性分析，未批准采购、采集部署、健康算法集成、心率 RTL 或模型替换。需要真实数据与对照实验后才能讨论有效心率范围、误差和运动适应性。此前架构讨论没有因本记录自动恢复为实施任务。

### 1. 正式软件与已知现象

正式 demo 的 HDMI 开关当前为 false。display worker 实际生产 720p RGB 绘制和 NV12 视频帧，没有完成独立 HDMI sink。它保持 SDK-free 的子进程边界，不能为接 HDMI 直接引入继承的设备句柄或打破资源所有权。

### 3. SDK 包装与 RTL 的关键证据

HDMIDisplay 包装仅支持 RGB565，按 width×height×2 分配 UDMA 帧，写入像素后发布地址；构造时传入宽高不等于设置 HDMI 像素时钟或输出时序。没有已确认的翻帧完成或安全停止接口。

现有 PLin+HDMI 示例先创建 SDICamera，再创建 HDMIDisplay；camera.vtc 用于输入链路。直接复用完整示例会带入相机初始化、复位与输入资源，不适合尚未核验的独立 CSI 系统显示。示例解析 display.fps 也不构成实际编程帧率的证明。

本机参考 RTL 提供以下线索，但尚未证明与正在运行的 BOOT 同源同配置：

- `rx_sdi.v` 在 SDI 锁定时选择 rx_usrclk，否则回退 sys_clk_200m；该信号名不证明现场实际频率。
- `frame_to_ps_largebuf.v` 的 HDMI PCLKX1 直接来自 cam_clk_use；PCLKX5 来自 PLL。不能只看 PLL 的 148.5 MHz 输出名称就断言像素时钟正确。
- `video_define.v`／color_bar 固定为 1080p 分支，扫描总计 2200×1125；帧读取长度固定为 518400 个 64 位单位，即 4,147,200 字节，对应 1920×1080 RGB565。
- 输入 VTC 的 H/V 寄存器和 enable 作用于输入侧，不是已确认的 HDMI 输出时序切换接口。改输入 VTC 不等于改 HDMI 时钟和扫描尺寸。
- 四路读地址在该层接为同一个 camera_rd_addr；读完成信号在上层未连接，不能因此宣称存在软件可用的四缓冲或翻帧完成通知。
- disable_hdmi 会跨时钟域控制显示信号，也影响其他数据路径；它并非已验证的 DDR 停止／drain 证明。不得据此立即释放 DMA 缓冲。

因此，目前最需要核验的是无 SDI 时实际时钟与 PLL 条件、当前 BOOT 对独立 PS 显示的支持，以及缓冲读取、翻帧和安全退出契约。软件 720p 帧若直接交给固定 1080p 读端，存在尺寸不匹配；地址可写或工具返回成功不能当作显示通过。

完整静态取证见 [HDMI 资源审查报告](tools/pose-v1/evidence/hdmi-resource-audit-20261015-r1/REPORT.md)，含源码入口、38 项文件身份及 BOOT／bit 对照结果。该报告为本机分析，未执行新一轮板端显示。
