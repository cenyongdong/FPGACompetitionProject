# 用户提供 H2testw 结果的分析

## 工程内容总结

结果由用户自行运行并提供文本和截图，H2testw界面1.4，测试E:当前FAT分区可用950MiB，分区总1023MiB。115MiB正确读回，835MiB未正确读回，约87.9%测试数据失败；包括覆盖/损坏和地址别名报告。首个错误在测试数据偏移0x07300000，即115MiB；不能把该测试数据偏移当成整张卡物理起始偏移。115MiB OK也不能认定为卡的真实容量，不能仅此宣布128MB扩容卡。

这是独立于系统镜像写入的测试文件写/读不一致证据。与此前两只读卡器上的8/9启动文件内容异常相符，当前存储链路不适合做启动介质，已不是纯粹uEnv编码显示问题。当前电脑仍枚举新读卡器序列号000000000819；测试截图未独立显示硬件身份。结合用户更换读卡器后问题仍复现，SD卡本身的质量/控制器/容量异常成为首要怀疑对象，但精确根因与假容量尚未确诊。

截图只测试约1GiB FAT分区的可用空间，不是此前准备的清卡后单分区全64GB方案，不能写作完整容量验收。但局部严重失败已足以判定本次读写不可靠，不必为证明当前启动卡不合格而继续重复整盘写入。

仅进行报告解读、当前设备只读枚举和证据保存；没有代理运行格式化、H2testw、重新烧录或写板端内容。此前全容量测试方案仍未由本代理执行。证据user-result.txt、user-result.png、interpretation.json。

## 对后续开发的参考

1. 实际读回数据错误、地址别名、数据被覆盖可解释启动文件无效及无法正常启动。应优先停用这张卡并向卖家提交测试截图和前述文件比对证据，换卡后重新验证；不将更换/退货建议视作已执行。
2. 真容量验收需测试整个可用空间；局部失败可拒绝介质可靠性，但局部通过不能证明完整容量，115MiB OK不是可安全使用容量承诺。
3. 对根因作最终归属，可用新读卡器在同一USB口测试另一张已知正常卡，或在另一台电脑复核当前卡。后续覆盖写入仍须核对目标并明确批准；不自行缩容或修BOOT。
