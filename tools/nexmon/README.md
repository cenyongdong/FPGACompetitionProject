## 10月21日重复身份离线排查

**已完成已有PCAP、发送台账及固定版本源码排查；短时无线重传是当前最有依据的假设，仍未确证。** 本轮没有连接设备或进行新采样。诊断见[结构化结果](evidence/5ghz-300hz-20261020-r1/identity-diagnostic-20261021.json)、[192次事件明细](evidence/5ghz-300hz-20261020-r1/identity-diagnostic-20261021.csv)和[离线入口](host/diagnose_identity.py)。原PCAP、NPZ、严格验收结果及模型输入契约均未修改，没有输出去重后的数据集。

- 直接按UDP负载字节偏移独立读取头部，与原导出的全部18,606条CSI、6,202组事件、原始CSI字、序号、信道、逐链到达时间及重复标记一致。固定源码从802.11头`MAC_OFFSET + 22`取得完整Sequence Control；未发现字节序、链号、分片号截断或事件重排错误。
- 192次标记全部与前一个事件同身份，形成177段连续同序号记录：168段各2组、3段各3组、6段各4组。额外事件数为`168×1 + 3×2 + 6×3 = 192`，对应原严格检查的`192×3 = 576`条重复core记录。相邻重复到达间隔0.020～1.272 ms，中位0.321 ms；最长一段跨度1.616 ms。将诊断窗口从20 ms缩到2 ms，计数仍为192；这批标记不是20 ms窗口过大直接造成。
- 排除被PHY状态覆盖的28～30号字后，每次重复对比的183个原始CSI字全部有变化，未发现同一份CSI的原样复制。这不能单独证明独立RF采样，也不能排除固件身份复用。唯一的4095→0序号回绕没有被标记为重复。
- 另有13处序号步长为2、到达间隔6.634～6.888 ms；它们与192次短时重复分开记录。缺失字段和未知帧类型使其不能直接解释为13个测试UDP丢失，更不能以录制器内核丢包0认定没有采集遗漏。发送台账仍是6,000个不同槽位各发送一次。
- 20点滑动窗口中有863个包含重复标记。全录制窗20点首尾间隔最短14.290 ms，300 Hz理想值为63.333 ms；仅作诊断性“同身份取首份”对照后最短为53.867 ms，仍不均匀。该对照没有剔除背景或校正接收时间，不能当作已修复的模型输入或实际RF采样时间。

源码依据为固定提交`1232edf2cf1e7ae0561676c49e4dd4eb22c8a27e`，本机相关C／微码文件无改动。BCM4366分支将`fc`初始化为0，此后未写入原始Frame Control；18,606条记录的该字节确实全为0，且没有QoS TID或RF TSF。微码先清除`DUMP_CSI`，再按core／stream读取表；C侧每条core完成4个20 MHz分块后发出一次并清空缓冲指针，未发现显式重复发送完整事件的代码，但静态检查不能排除运行中的关联问题。[Linux原生重复检测](https://github.com/torvalds/linux/blob/master/net/mac80211/rx.c)使用重传位及按QoS队列区分的序号，当前简化身份不具备相同信息。PHY状态是从普通接收路径全局复制的值，不当作完整无线头或当前事件硬件时间使用。

另已确认[录制器](router/capture_udp5500.c)只保留CSI UDP/5500，并在用户态`recvfrom`后读取`CLOCK_REALTIME`；原始802.11头、UDP测试槽位及RF时间无法从这份PCAP补取。两端没有共享时钟，发送QPC日志也不能逐条对应接收事件。因此保持原`acquisition_pass=false`及`model_ready=false`。不能仅凭本轮异常判断人体识别成败，尚无模型实测。

下一阶段方案：沿用自有手机5 GHz热点＋笔记本客户端＋路由器监听的已验证拓扑，先短时检查现有monitor接口是否能同时输出原始802.11头；可见后再做一轮300 Hz／10秒有界发包，同步保留Frame Control／retry、发送地址、Sequence Control、QoS TID、可用的聚合／硬件时间信息及CSI。若原始头不可见，先停止受控发包并报告缺失，不先改固件或更换设备。需据这些字段区分真正重传、不同队列身份碰撞与固件上报关联；按约定先汇报该方案，再由用户指示推进实机取证。

这证明了**本轮20秒内的300 Hz发送调度、IP投递以及真实三链接收能力**。发送完成不是独立RF帧证明，内核丢包0也不是空口无损证明；CSI中仍有背景流量和重复身份，尚未把每个UDP槽位对应到唯一无线训练字段。不能把17,196除以三当作独立样本数，也不能由5,732与6,000的差值计算空口丢包。原始CSI时间仍是接收端OS到达时间；全接收窗事件间隔p99为39.75 ms，不能称为均匀3.333 ms采样。下一步应先区分背景帧、聚合／重传和身份字段，再评估实时窗口。

初次程序使用`Thread.Sleep`时，300 Hz／10秒只发出873包、跳过2,127个槽位，全部成功投递；该失败保留在[首轮记录](evidence/mt7922-tx-20261020-r1/run-summary.json)。改用显式高分辨率waitable timer后通过上述实机检查，不将初次调度失败归因于网卡硬件。[微软说明](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)指出Windows 11可能降低被遮挡／最小化GUI的定时分辨率；这是与现象相符的机制，未单独证实为该机唯一原因。工具为[有界发射程序](host/LaptopTx.cs)、[临时控制与投递台账](host/laptop_tx_control.py)、[只读笔记本预检](host/laptop_preflight.ps1)及[临时LAN侧SSH放行工具](host/LaptopSshAccess.cs)。无需安装Python到笔记本。

结束时已核验路由器两频段原运行固件恢复、monitor为0、看门狗退出；笔记本两项驱动原值0／0已写回，独立的网卡重启工作进程完成，最终现场协商制式因SSH入口关闭未重新读到。台式机控制端和本机密码进程已关闭。自动审批拒绝了自动关闭笔记本SSH服务与临时窗口的命令，已请用户手动完成；确认状态以本轮汇总为准。用户自行修改的台式机LAN地址保持。

本轮未改原`[3,3,30,20]` RAW、`[1,180,60]` tokens、模型结构／数学、SDK、NPU分配或板端帧协议，未进行模型推理。一台路由器仍只代表一个独立接收节点；未复制节点、补造样本或改变30子载波预处理。FPGA／HDMI及旧DATA任务均未恢复。
